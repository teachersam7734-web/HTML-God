# Tools, skills, recovery and durable handoffs

## Capability inventory

Inspect available tools and installed skills before proposing installation. A plugin's name is not evidence that a specific API is callable. Prefer the actual capability: native image generation for imagery, file/CLI tools for local builds, a real browser for UI QA, primary-source web tools for current documentation, and a PDF renderer for page inspection. Do not imply a unavailable plugin rendered an output.

Useful skill roles in the original project:

| Mega Study Method | Lesson sequence, cue maps, retrieval/application/trace practices | Adapt to the requested course format; do not invent neuroscience claims |

This skill summarises useful operational lessons instead of redistributing every installed skill's full text. Future agents should read whichever corresponding skill is actually available and applicable. Absence of one preferred plugin does not automatically block a project that can be completed with an authorised alternative.

## Actual tool families used

- File/terminal execution: discovery with fast file search, source reads, patching, bundling, hashes, manifests and inspection scripts.
- Built-in image generation: original bitmap production; images copied to project assets after inspection.
- Web research: official sites, GitHub repository/docs/licences and a research connector where available. The Firecrawl CLI was not always usable; alternate available web tools were used.
- Browser automation: local Playwright/Edge, screenshots, actual UI actions, offline context, console/page errors and touch emulation.
- Media tools: FFmpeg/ffprobe, native image/Python libraries for authorised video preparation and metadata.
- Collaboration: bounded content, asset, motion and QA tasks with saved output/report paths. Later dispatches failed due to agent workspace credits; direct work continued.
- Workspace dependency discovery: located bundled Python/Node/PDF/browser libraries instead of assuming globally installed packages.

Tool names vary by host. Translate these roles into the current environment rather than baking a previous machine's executable path into portable code. The included helpers accept command-line arguments or environment overrides for this reason.

## Delegation only when authorised and useful

Useful independent tasks include: source coverage plan; a bounded chapter batch; asset production from an approved brief; licence/source verification; one scene family; mobile/keyboard QA; or final source-fidelity audit. Do not spawn a second agent merely to restate the whole task.

Give each task a scope, exclusive output paths, acceptance criteria, shared schema/design tokens, source inputs and reporting cadence. Ask it to save files before reporting. A useful checkpoint contains completed outputs, exact filenames, validation performed, open issues and next action. Agents should not overwrite a shared master file without a coordination plan.

Integrate small verified batches. Check reports against actual files and executable outputs. A claimed render needs a media file and metadata; a claimed QA pass needs reproducible assertions or evidence. Preserve the report even if the work is later revised. If an agent is blocked, continue unaffected work and record the limitation.

## Recovery patterns

- **Missing executable:** inspect the bundled runtime or dependency paths first. Install only what is needed when permitted; do not duplicate entire toolchains.
- **Network/cache restriction:** use existing pinned dependencies or an available official-source connector. A failed CLI attempt does not prove a package was installed.
- **Browser launch restrictions:** follow the host's execution/approval mechanism. Do not turn a failed launch into an untested claim. Use an authorised alternative browser only if appropriate. Close only the browsers you opened; never kill a browser by image name, which also closes the user's own windows.
- **Large HTML:** avoid terminal-dumping its embedded media. Inspect source modules, parse selected metadata and use streaming hashes.
- **Long render:** save intermediate status and artefact paths, wait in bounded intervals, and keep the user informed without repeating unchanged logs.
- **Context compaction:** maintain an on-disk handoff with original goal, latest steering, completed work, preserved constraints, current build path, failing checks and exact next steps. Do not restart from scratch.

## Windows and shell lessons

Treat commands as code. Use structured arguments or temporary files for multiline descriptions. PowerShell and shell quoting rules differ; JSON escaping does not make a string safe for a shell. Avoid variable names that collide with system variables. Use one shell and literal paths for file operations; verify resolved targets before recursive moves/deletes. Hidden background helpers should not surprise the user with visible windows.

For Python scripts containing non-ASCII prose, use UTF-8 files and a UTF-8 runtime invocation where needed. Do not let terminal encoding silently replace punctuation or names. Prefer deterministic patch/file APIs for large code blocks over fragile one-line nested quoting.

## Communication and completion

Start a substantial task with a concise action statement. Report meaningful findings and remaining uncertainties during work. Avoid repeatedly asking permission for actions the user already authorised. A real blocked action should be identified precisely with its reason and source, not dressed up as a vague need for confirmation.

The final response should present the finished artefact, the meaningful changes and the scope of testing. Distinguish source code from delivered media, direct QA from independent review, and installed dependencies from inspiration. If the user requires approval before manuals, publication or follow-up packaging, respect that ordering. In this case the manual and reusable skill began only after explicit course approval.
